# 第 17 章　平台、券商与基础设施

!!! abstract "本章要点"
    - 自动化交易的大多数“事故”来自**基础设施而非策略**：订单状态、保证金口径、数据分辨率、平台升级。
    - 社区经验：先把流程搭起来（回测、纸盘、小额实盘），再谈优化；开发循环的速度比平台的功能更重要。
    - 开源平台（QuantConnect/LEAN、NautilusTrader）与自建系统各有取舍；真正困难的是**与券商的订单管理（OMS）状态同步**。
    - 语言之争（C++、Java、Go、Python）的实质，是延迟预算与迭代速度的取舍。
    - 某些“高胜率”说法需要代入公式：99.5% 的胜率只要有一次足够大的亏损就能抹平。

## 17.1　概念：把交易系统拆成几层

一个可以实盘的系统，大体包含：

1. **数据层**：行情、期权链、历史数据、复权与时区处理；
2. **信号层**：策略逻辑；
3. **组合与风控层**：目标仓位、风险限额、断路器（第 9 章）；
4. **执行层**：订单类型、路由、状态机（新单/部分成交/成交/撤销/拒绝）；
5. **对账层**：本地持仓与券商持仓的一致性（OMS 同步）。

事故多发生在 3–5 层；而回测框架往往只覆盖 1–2 层。这就是回测与实盘的差距的结构性来源（第 6 章）。

## 17.2　平台使用中的“小坑”：来自 QuantConnect 论坛

- **实盘订单状态异常**（2016）：在一个 SMA 交叉的两标的轮动策略里，回测执行良好，但实盘第三笔时买单没有被执行；问题涉及部分成交后未收到最终事件、翻转仓位失败；建议为市价单设置成交超时，并按订单类型分别处理。来源：[Invalid order status in live trading](https://www.quantconnect.com/forum/discussion/984/invalid-order-status-in-live-trading/)（QuantConnect，2016-01-13）。
- **MarginRemaining 与券商买入力不一致**（2020）：IBKR 保证金账户里，平台的 `MarginRemaining`（按结算现金为负）与 IBKR 的 Buying Power 不一致，导致多笔市价单因保证金不足被拒。官方回复：算法部署时会取账户当前持仓，LEAN 重建投资组合时把现金余额当作 MarginRemaining，因此对使用 universe selection 的算法，**建议用“干净”的投资组合部署**。来源：[Negative Margin Remaining but IBKR Shows Positive Buying Power](https://www.quantconnect.com/forum/discussion/8599/negative-margin-remaining-but-ibkr-shows-positive-buying-power/)（QuantConnect，2020-07-01）。
- **风控模型与 insight**（2020）：风险管理模型平仓后，如果原来的 insight 仍然有效，组合模型会重新开仓；需要自定义风控模型，记录已平仓的标的，并在新的 insight 发出时重置。来源：[Risk Management Models and Insights](https://www.quantconnect.com/forum/discussion/8355/risk-management-models-and-insights/)（QuantConnect，2020-06-05）。
- **数据分辨率**（2015）：早期平台没有日线，需用分钟数据合成；fill-forward 会在无数据时重复 K 线。来源：[Daily resolution vs Minute resolution](https://www.quantconnect.com/forum/discussion/519/daily-resolution-vs-minute-resolution/)（QuantConnect，2015-05-13）。
- **二元期权策略**（2015）：60 秒 BB 的二元期权不适合在平台回测；建议用胜率/赔率近似；平台并非为二元期权设计。来源：[Binary Strategies?](https://www.quantconnect.com/forum/discussion/447/binary-strategies/)（QuantConnect，2015-03-07）。
- **平台升级造成的 bug**（2021）：回测突然报 KeyError，官方称是上线新 pandas 带来的索引问题，已修补——属平台问题而非用户代码。来源：[Problem with Backtest (maybe a Bug)](https://www.quantconnect.com/forum/discussion/12054/problem-with-backtest-maybe-a-bug/)（QuantConnect，2021-07-30）。
- **开发循环**（2019）：“QC 上开发痛苦地慢”：每次回测至少 20–30 秒；Research 里不能测试 universe selection；平台创始人回应在优化；评论称问题更在于反复回测来加 debug。来源：[Is it just me or is it painfully slow and complicated to develop on QC ?](https://www.quantconnect.com/forum/discussion/5206/is-it-just-me-or-is-it-painfully-slow-and-complicated-to-develop-on-qc/)（QuantConnect，2019-01-25）。
- **复现“In-Out ROC”**（2021）：QC 论坛里一群人复现某高收益算法，发现收益强烈依赖选股组合，难以复现原作者的最优结果；有人改写成期权版本（买入 X% 价外、Y 天到期的看涨期权），并建议重构后再考虑实盘。来源：[Reproducing In-Out with ROC v1.9](https://www.quantconnect.com/forum/discussion/10763/reproducing-in-out-with-roc-v1-9/)（QuantConnect，2021-02-25）。

!!! note "作者注"
    这些问题没有一个是“策略问题”。如果你在做 0DTE 实盘，**实盘前请至少做一次“混乱测试”**：断网重连、部分成交、拒单、保证金不足、平台升级后重新部署。

## 17.3　自动交易系统怎么搭（早期论坛）

2008 年的 Elite Trader 里有两个关于“设计盈利的自动交易系统”的帖子（[Designing and Building a Profitable Automated Trading System](https://www.elitetrader.com/et/threads/designing-and-building-a-profitable-automated-trading-system.147441/)（Elite Trader，2008-12-09），基于随机指标与 MACD 的开发者招募；[How to Build an Automated Trading System](https://www.elitetrader.com/et/threads/how-to-build-an-automated-trading-system.136434/)（Elite Trader，2008-09-14），“如何搭建自动交易系统”，偏软件架构：状态机与 Hershey 通道）。它们的共同点是：**大部分内容是对 Jack Hershey 式指标/通道交易的讨论，绩效信息量低**，对本书最大的价值在于架构思路：把“人类做的事”拆成状态机。来源：[Designing and Building a Profitable Automated Trading System](https://www.elitetrader.com/et/threads/designing-and-building-a-profitable-automated-trading-system.147441/)（Elite Trader，2008-12-09）；[How to Build an Automated Trading System](https://www.elitetrader.com/et/threads/how-to-build-an-automated-trading-system.136434/)（Elite Trader，2008-09-14）。

## 17.4　开源平台与自建系统

HN 2025-08 的 NautilusTrader 帖（127 条评论）里有几条值得保留：

- 一位交易了近 6 年加密货币的人（最好的一个月成交额 60 亿美元）说：**常规的策略没有一个持续有效**——回测调参、带特征选择的 ML、boosting、神经网络，全部样本外失败；真正有效的是“清晰的 edge”：高成交量团队的私有交易所返佣计划、纯延迟套利、冷门工具的套利（如链上 AMM 与交易所期货）；做市和套利策略对延迟都很敏感，他们用 Java 与 Chronicle-Queue 自建低延迟引擎，**从市场事件到下单在热点循环的 99.99 分位约 130 微秒**（原文的单位被写成“mqs”，应为微秒级，此处按帖中数字转述）。
- 一位量化公司员工指出：**集成与 OMS 同步是难点**。
- 一位自称卖期权的评论者称，他曾有 99.5% 的胜率，但那 0.5% 的事件抹掉了所有收益。（Canvas 汇总的摘要；评论原文本书未能完整读取。）

**自洽检验**（本书作者）：设盈利笔数占比 99.5%，平均每笔盈利 $w$，亏损笔数占比 0.5%，平均每笔亏损 $L$。期望为 $0.995w-0.005L$，令其为 0，得 $L=199w$。也就是说，**只要一次亏损的金额超过一次盈利的 199 倍，就足以把期望转负**——对于卖深度虚值期权的人，这一点毫不夸张。来源：[NautilusTrader: Open-source algorithmic trading platform](https://news.ycombinator.com/item?id=44810552)（Hacker News，2025-08-06）。

- **QuantNet 上的 C++**（2008）：Duffy 给出的理由是：灵活/可互操作、成熟的多范式、ISO 标准；其他人说实时计算的速度；也有怀疑者认为 C++ 的主导地位是历史偶然与遗留代码。来源：[Why is C++ good for Quantitative Finance? Top 3 reasons](https://quantnet.com/threads/why-is-c-good-for-quantitative-finance-top-3-reasons.1116/)（QuantNet，2008-01-26）。Duffy 关于 C++11 与计算金融的系列文章见 [Blog: Articles on C++11 and Computational Finance (Duffy)](https://quantnet.com/threads/blog-articles-on-c-11-and-computational-finance-by-daniel-j-duffy.32237/)（QuantNet，2017-10-29）。来源页的文本本书未能完整读取，仅依据早先摘要。
- **JPMorgan CDS 分析引擎开源**（QuantNet 2009）：见 [J.P. Morgan's CDS Analytical Engine Available as Open Source](https://quantnet.com/threads/j-p-morgans-cds-analytical-engine-available-as-open-source.2295/)（QuantNet，2009-01-29）（同上，仅依据早先摘要）。
- 第 15 章里 HN 上的 Java/C++/Go 帖子（[We chose Java for our high-frequency trading application](https://news.ycombinator.com/item?id=24895395)（Hacker News，2020-10-26）、[C++ patterns for low-latency applications including high-frequency trading](https://news.ycombinator.com/item?id=40908273)（Hacker News，2024-07-08）、[Case study: Algorithmic trading with Go](https://news.ycombinator.com/item?id=36539235)（Hacker News，2023-06-30））与此互补：低延迟不是语言问题，而是**热点路径上有没有内存分配、锁与系统调用**。

## 17.7　本章小结与自查清单

!!! success "小结"
    把“基础设施风险”当成与“市场风险”同级的风险：每一次实盘事故，都应当变成一条自动化测试或一条监控告警。

!!! tip "自查清单"
    - [ ] 我的系统有订单状态机，并处理部分成交、拒单与超时吗？
    - [ ] 本地持仓与券商持仓是否定时对账？
    - [ ] 我知道平台的保证金口径与券商是否一致吗？
    - [ ] 平台或依赖库升级前，我有回归测试吗？
    - [ ] 我有“断网、重启、拒单”的演练记录吗？
